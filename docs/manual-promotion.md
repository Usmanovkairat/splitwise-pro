# Manual promotion

A trusted push to main runs verification, infrastructure and observability tests. The release-development job publishes a GHCR candidate, starts the exact image digest in its own PostgreSQL Compose project, checks readiness, and runs Playwright against that digest. Only a successful job uploads the release metadata. The runner database is disposable.

The workflow files must first reach the default branch through review. Configure GitHub Environments named `development` and `production`, allow deployment only from main, require reviewers for production, and turn off self-approval where supported. Set `DEPLOY_ENABLED=true` only in the production environment after setup. Add `GCP_PROJECT_ID`, `GCP_ZONE`, `GCP_VM_NAME`, `GCP_WORKLOAD_IDENTITY_PROVIDER` and `GCP_DEPLOY_SERVICE_ACCOUNT` to production. Configure GCP OIDC and protected IAP access as documented in [cloud prerequisites](../deployment/CLOUD.md). The VM needs pull access to the GHCR package. With the existing deploy script this means anonymous package pulls. Review package visibility before changing it.

1. In Actions, open a successful **Verify SplitWise Pro** run triggered by a push to main. Its summary must show the verified digest.
2. Run **Promote verified development image** on main and enter the numeric run ID. The workflow validates the repository, workflow path, trigger, head branch, successful conclusion, run attempt, and digest metadata. Expired metadata requires a new verified run.
3. Review and approve the production deployment in GitHub. The release script pulls the recorded digest, makes a PostgreSQL backup, updates the app container, and verifies readiness through the protected host. The job summary records the healthy release revision and digest.
4. If the rollout fails, inspect the image rollback output and the path to the protected backup. To revert a healthy rollout, dispatch an earlier verified run with retained metadata and image. Review migration compatibility before any rollback and database restoration. A backup restore can overwrite newer records and requires explicit authorization.

By default the current protected VM template has app and PostgreSQL only. To collect production telemetry, copy `compose.observability.yaml`, `observability/` and `oncall/` into `/srv/splitwise/config` on the protected host. Check the host can support the monitoring services. Add `SPLITWISE_ENVIRONMENT=production`, the production Grafana password and a production webhook token to that directory's restricted Compose environment file. Build the responder with `docker compose -f compose.yaml -f compose.observability.yaml build oncall`, then set `COMPOSE_FILE=compose.yaml:compose.observability.yaml` in the same environment file. Review the overlay against the existing host Compose file before enabling rollout. Keep the production host and deployment identity isolated from development. No live host, public URL or completed cloud rollout is asserted.
